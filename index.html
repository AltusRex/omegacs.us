01How I think

The rules I build by

These come from fixing the same problems more than once. They show up in everything I make, from a document generator to a home firewall.

  • Simple beats clever.

    I'll take a little less automation over a lot more architecture.

  • Low variance.

    A process should work in almost any environment without per-case tweaking.

  • Search before you build.

    Reuse what exists. Write something new only when nothing fits.

  • Nudge, don't block.

    When the data is messy, the tool asks you to fix it instead of refusing to run.

  • Same input, same output.

    A generated document shouldn't depend on who ran the tool or which AI built it.

  • Read-only by default.

    Tools look before they touch. Nothing changes until a person says yes.

  • Accuracy where mistakes are expensive.

    A bad config mapping costs hours of troubleshooting later, so that's where I spend the extra checks.

  • Built for the next maintainer.

    Documented and structured so another person, or another AI, can pick it up cold.

02How I build

Spec first, then let the machine type

I'm strongest at logic and at seeing a problem from an odd angle. AI fills the hands-on coding gap. The loop looks like this.

  1. Find the friction

    Something takes too long, breaks the same way twice, or nobody has bothered to fix.

  2. Write the spec

    What it does, what it must never do, and how I'll know it worked.

  3. AI builds, I review

    Agents write the code. I direct, read the diffs and approve.

  4. Prove it on real data

    A quick go or no-go test before I sink more time in.

  5. Ship small, keep patching

    Other people use it, report what breaks, and I version it forward.

03What I build

AI tooling for real work

At my day job I build tools for other technicians and the people they support. The specifics belong to my employer, so this is the shape of the work rather than the details.

Skills that turn a process into a tool

In daily use

Packaged AI skills that draft scopes of work, engineering plans, bills of materials and client status reports. Each one produces the same structure no matter who runs it, and the status reports can run on a schedule as drafts for review.

Connectors that let AI read business systems

In daily use

MCP connectors that give AI read access to the ticketing and documentation systems a tech lives in.

  • Read-only by default, with per-user keys. Write tools exist but stay off unless someone turns them on.
  • Built by CI and published as releases, so installs update themselves.
  • Sensitive fields are excluded on purpose. The connector reports that a secret exists, never what it is.

A fleet of single-purpose agents

Running

A set of AI bots where each one has one job - tracking my time, catching messages that slip through, scouting a project before it starts, watching our own tools for known vulnerabilities. An orchestrator bot helps me build and maintain the rest.

  • A desired-state baseline rebuilds a bot's machine after a wipe, with minimum versions pinned for security.
  • Proposed fixes wait on an approval list until I sign off.
  • Teammates don't need to know which bot does what. One front-door bot routes the request.

A config migration mapper

In production

Takes one firewall vendor's config export and produces a mapping workbook and a click-path build guide for another. The output is checked three ways - against the target's API schema, against an independent re-read of the export, and with a traffic simulation. Other techs use it on live migrations and I patch it from their reports.

Debugging the tool that helps AI read my code

Fixed upstream

My game's AI workflow runs on vexp, a context engine that gives coding agents a pre-indexed, ranked view of a codebase so they don't have to grep around and burn tokens. On a 120,000-line C# project it wasn't returning the right context, so I took it apart and worked with its developer directly. Over two days and four releases I sent four reports, each with a repro package and debug traces.

  • Search found no C# code at all. I queried the index database directly to prove the data was there and scoring well, then traced the failure to how the search layer handled C# names like CombatActor. The developer adopted the fallback I suggested - promote strong keyword hits when the semantic score comes back empty - and shipped fixes in the next release.
  • The fix worked for some classes and not others. I ran a passing class and two failing ones through the pipeline side by side and showed exactly which step dropped them.
  • 22,000 call-graph edges were collected but never read. A changelog said this was fixed. The debug trace showed the impact query never touched that table, because the editor and the indexer wrote function names in two different formats.
  • A view everyone would read backwards. I documented that the blast-radius section listed what a class calls, not what calls it, so nobody would trust it for the wrong job.

"This is one of the most useful bug reports we've received... seriously, thank you for the depth here; it made our job easy."

Nicola Alessi, vexp developer
